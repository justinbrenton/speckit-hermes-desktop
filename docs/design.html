Spec-Kit for Hermes Desktop

Status: working implementation, pre-release. This document describes what exists, what it does, and what is deliberately not built yet. Every claim in the "Verification" section came from a command that ran on this machine.

Last updated: 2026-10-24.

1. What this is

Spec-Kit is a specification-driven development toolkit: write a spec, derive a plan, break the plan into tasks, implement. Upstream (github/spec-kit) does that with markdown templates and CLI commands. Everything lands in a .specify/ directory, and you carry it between your editor, your terminal, and your agent by hand.

This project puts the same workflow inside Hermes Desktop as one guided pane. You describe the feature in a sentence, the workflow's own steps run one at a time, and every review gate stops and asks you before the next step. The files on disk stay the source of truth, so anything else that reads .specify/ or specs/ still works.

The scope is narrow on purpose: one pane, one project at a time, and no workflow logic in the pane itself.

2. Why not just install spec-kit and use the CLI

Because the loop breaks at the handoff. Stock spec-kit gives you files, and then you are on your own: read spec.md, work out what changed, retype it into a prompt, run a command, come back, read tasks.md, find which checkbox is yours. The documents are correct and the workflow is still manual.

Stock spec-kitThis
You remember which command comes nextThe workflow's steps are the UI; the next action is the only button on screen
Gates are an interactive terminal promptA gate card with the declared options; approving resumes the run
You read the terminal to know what happenedA step tracker, plus the run's own state read off disk
Artifacts are files you go and findThe artifacts the run wrote are listed in the pane, read-only
A gate cannot be answered headlessverdict_input is added to generated gates, so resume works without a TTY

What it does not do: replace spec-kit. Templates, preset, extension hooks and the workflow all still come from the fork. The pane is the surface on top.

3. What exists today

Two halves, because that split is the only supported way for a desktop plugin to touch files. The renderer has no filesystem access, and the gateway JSON-RPC surface has no read or write method.

The pane reaches the backend through ctx.rest, which Hermes scopes to /api/plugins/spec-kit-hermes. The routes the pane uses:

POST /workflows/{process}/runspawn a run, return a job id at once
GET /workflows/{process}/runs/latestnewest run's status, step, gate

GET /artifactsevery artifact the run has written

Reads and writes of whole files (/files, /file) and the Kanban routes (/kanban/sync, /kanban/links) still exist from the editor era; the wizard does not call them.

Three plugin kinds exist, and mixing them up caused most of the confusion in earlier drafts:

This project is a desktop plugin with a dashboard backend. desktop/plugin.yaml ships for packaging and version metadata; the disk loader does not read it, so there is no config_schema here and settings belong in ctx.storage. The backend half does need its plugin id in plugins.enabled, which is why the installer edits config.yaml.

4. How a session actually runs

open the pane on a project
   │  GET /processes  ──▶ installed workflows, their inputs, their steps
   ▼
describe               one textarea: what are you building?
   │  POST /workflows/<process>/run   ──▶ specify workflow run … --json
   ▼
steps                  the engine executes; the pane polls /runs/latest
   │                   command step → runs the agent, writes the artifact
   │                   gate step    → status: paused, the pane asks you
   │  POST …/runs/<id>/resume  -i gate_review_spec=approve
   ▼
artifacts              read-only, from <project>/specs/ and .specify/memory/

One screen, one decision at a time. The step tracker at the top shows where the run is; the card below it is the only thing you can act on: Start, wait, approve or reject. There is no separate "pick a process" screen in v1 — the pane drives the speckit workflow and lists whatever else is installed once process choice matters.

Requests return immediately. A step dispatches a model call that can run for minutes, and the desktop's RPC bridge gives up at 30 seconds, so run and resume spawn the CLI and return a job id; the pane polls GET /workflows/<process>/runs/latest every two seconds while the engine works.

The pane authoring three files by hand is gone. spec.md, memory/constitution.md and tasks.md are written by /speckit-specify, /speckit-constitution and /speckit-tasks inside the workflow, so there is one way to produce them and one place they come from. The pane still reads files, but only as artifacts.

What the pane does not do, on purpose: run steps itself, decide what a process means, or invent a gate. It reads the workflow, posts to three routes, and renders what comes back.

Where artifacts actually land

specify init scaffolds .specify/, but the skills write feature folders to <project>/specs/<NNN>-<name>/ — not .specify/specs/. The artifact listing scans both locations plus .specify/memory/constitution.md, and the reader refuses any path outside them.

Gates need verdict_input

A gate can only be answered from outside a terminal when its workflow declares which input carries the verdict:

  - id: review-spec
    type: gate
    message: "Review the generated spec before planning."
    options: [approve, reject]
    verdict_input: gate_review_spec   # resume -i gate_review_spec=approve
    on_reject: abort

The engine checks "verdict_input" in config (see workflows/step/gate/), so a stock gate without it ignores every -i you pass and pauses forever. init now patches every installed workflow after scaffolding, and POST /repair-workflows does the same for projects created earlier.

What was removed

src/core.mjs used to carry the parsers and models of the abandoned three-editor design: parseSpec/serializeSpec, parseTasks/serializeTasks, the constitution builder and validator, the Kanban derivation helpers, the stepper state machine and dispatchMessage. The wizard calls none of them — the skills write those files now. They were deleted with their tests; core.mjs is 105 lines of wizard model, and plugin.js lost roughly a third of its size in that pass (the sizes are in the commit).

The wizard's decisions are testable

The pane's judgement calls — which inputs to ask for, where the run is, which file a gate reviews — live in src/core.mjs as pure functions (visibleInputs, flowSteps, progressFor, artifactForGate) and are covered by npm test. That is where both reported defects came from: a gate whose id (review-spec) does not follow its step's name (specify), and verdict carriers rendering as questions. Matching gates by position, not by name, is the fix the test forced.

The clarification interview

spec-kit marks ambiguity inline as [NEEDS CLARIFICATION: ...], and its own guidance is to resolve those by editing the artifact or telling the agent. The pane turns them into a form instead: GET /questions lists the markers in the open artifact, POST /clarify writes the answers back in place and reports how many are still open. Unanswered markers survive, so the file never claims more certainty than it has.

Answers replace the marker where it sits, so text around it stays. A marker at the end of a sentence reads naturally; one embedded mid-clause can read awkwardly ("Shared team account accounts"). Editing the file directly is still the escape hatch, and the editor is right there.

A step that writes nothing is a failure, not a success

The engine reports a command step completed when its dispatch exits 0, even if the agent wrote no artifact. specify workflow run gave exactly that during testing: exit_code 0, stdout "", and the only reason the constitution stage was known to work was that the file changed.

So the backend snapshots artifact mtimes (specs/, .specify/specs, .specify/bugs, .specify/assessments, .specify/memory) before each run and resume, and GET /runs/... compares. When a gate is reached and nothing changed, the pane says so before you approve. It is a warning, not a hard failure: some steps legitimately edit nothing (analysis is read-only).

You can watch a step work

A dispatch runs for minutes with nothing on screen. GET /log tails the newest job log for the project (the same file the backend already writes for every spawn), and the pane polls it every two seconds while a step runs, behind a "Show log" toggle. Failures usually announce themselves there first — a missing skill, an auth error — long before the artifact is checked.

Run history

GET /workflows/{process}/runs lists every run on disk with its status, step and the input that started it. The pane shows the last few under the artifacts, so a previous attempt is identifiable by what it was asked to build rather than by a hex id.

One run at a time, and a way out

POST /workflows/{process}/runs/{id}/stop kills the dispatched process tree for that project only, and a second Start while a run is active returns 409. Without the lock, two clicks produce two concurrent runs writing the same files.

4.1 Processes: what the pane renders

Spec-kit is not one flow, and the pane must not pretend otherwise. It ships three independent entry points and makes adding a fourth a configuration exercise:

ProcessStepsShips asArtifacts
Spec-driven developmentconstitution, specify, plan, tasks, implement, converge (+ clarify, checklist, analyze as gates)core.specify/specs/<feature>/
Bug fixingassess, gate, fix, testextension bug + workflow bugfix.specify/bugs/<slug>/
Idea assessmentintake, research, define, shape, decide, gateextension assess + workflow assess.specify/assessments/<slug>/
Your ownwhatever you defineextension commands + a workflowwherever it writes

A workflow file is already the data model a GUI needs. Verified against workflows/bugfix/workflow.yml:

inputs:
  report:
    type: string
    required: true
    prompt: "Bug report (pasted text or URL)"
steps:
  - id: assess
    command: speckit.bug.assess
    input:
      args: "{{ inputs.report }} slug={{ inputs.slug }}"
  - id: review-assessment
    type: gate
    message: "Review the assessment before any code change."
    options: [approve, reject]
    on_reject: abort

Inputs carry their own prompts, so they are a form. Command steps carry their own argument template, so they are a dispatch. Gates carry their own message, options and reject behaviour, so they are a review panel. None of that needs per-process code in the pane.

GET /processes returns exactly this, discovered from <project>/.specify/workflows/*/workflow.yml. Each command step resolves to the skill the Hermes integration installs (speckit.bug.assess → speckit-bug-assess) and reports whether that skill is present, so a step can be disabled with a reason instead of failing when you click it. A malformed workflow is reported per file and does not take the pane down.

What the pane does with it:

  1. Pick a process. The list is whatever is installed: SDD today, bug fixing and

assessment when their bundles are installed, plus anything you write.

  1. Fill the inputs the workflow declares.
  2. Run the steps in order. A command step dispatches its skill with the rendered

arguments; a gate stops and waits for approve or reject.

  1. Show the artifacts the process wrote.

Rules that keep it expandable, in order of importance:

  • No process names in the pane. It renders installed workflows.
  • Gates are data. Options and on_reject come from the workflow, not from an if.
  • Artifacts are paths the process declares, not file names hard-coded in the UI.
  • Discovery goes through one route, so the CLI stays the source of truth for what

a workflow means.

Driving the engine, not reimplementing it

The plugin runs no workflow logic of its own. specify workflow run|resume|status --json is the engine, and the backend is a bridge to it:

RouteSpawns
POST /workflows/{process}/runspecify workflow run <process> -i k=v --json
POST /workflows/{process}/runs/{id}/resumespecify workflow resume <id> -i gate_x=approve --json
GET /workflows/{process}/runs/{id}specify workflow status <id> --json

Step types the engine supports beyond command and gate (shell, prompt, if, switch, while, fan-out, fan-in, github, init, slot, nested workflow) come for free, because the engine executes them. Run state, resume and history are already .specify/workflows/runs/<id>/ (state.json, inputs.json, log.jsonl), so the pane reads it rather than keeping its own.

Two Windows findings that shaped this, both measured:

  • stdin=DEVNULL does not pause a gate. NUL is a character device, so

sys.stdin.isatty() answers True, the gate prompts, reads EOF, and the run aborts with choice: reject. Passing input="" (a pipe that closes immediately) makes it pause. The bridge uses the pipe.

  • A gate can only be answered through a declared input. The schema rejects a

gate whose verdict_input is not in inputs:, and without one there is no non-interactive way to say approve. Our bundle's workflow declares one input per gate.

The loop, end to end on this machine:

run      -> status=paused   current_step=review-spec
resume -i gate_review_spec=approve
         -> progressed to review-plan (the plan step ran) and paused there

The first run also wrote a real spec through /speckit-specify: the engine dispatched hermes chat -Q -s speckit-specify and the pane-side output showed the model noticing it had resolved spec-template from the hermes-desktop preset.

Where the skills go

The docs say ~/.hermes/skills/. On Windows the home is %LOCALAPPDATA%\hermes, and a profile session reads <home>/profiles/<name>/skills; get_hermes_home() resolves context override, then HERMES_HOME, then the platform default.

Measured here, because this is where the integration silently failed: the ten skills were first installed to C:\Users\<user>\.hermes\skills and hermes skills list showed none of them. After copying them into profiles/codie/skills the listing showed ten and -s speckit-specify dispatched. So /processes checks every candidate directory and counts a skill as installed if any one of them has it.

The CLI already exposes the same inventory for the terminal: specify workflow list, specify extension list, and specify artifact for commands, templates, scripts and hooks. The pane reads the workflow files directly today because it needs inputs and step bodies, which those listings do not include.

7. What ships in the fork

justinbrenton/spec-kit is a fork of github/spec-kit. It carries the distribution layer, not the app. Every Hermes addition is a new directory plus a catalog entry.

extensions/hermes-desktop/    4 optional hooks, each implemented as a command
workflows/hermes-desktop/     8-step SDD workflow (command, parallel, loop steps; no gates)

Catalogs live at presets/catalog.json and friends, not in a catalogs/ directory. The four SPECKIT_PRESET_CATALOG_URL, SPECKIT_EXTENSION_CATALOG_URL, SPECKIT_WORKFLOW_CATALOG_URL and SPECKIT_BUNDLE_CATALOG_URL environment variables override them per machine or per CI job, which is how the fork gets tested without publishing.

The hooks:

HookCommandWhat it does
before_specifyspeckit.git.create-branchbranch for the feature
before_planspeckit.constitution.checkrefuse to plan against an unratified constitution
after_implementspeckit.converge.autoconvergence pass after implementation
after_convergespeckit.pr.prepareassemble PR context

All four are optional: true. A missing hook degrades; it does not break the workflow.

Adding something to the fork without publishing first:

specify preset add    --dev ./presets/hermes-desktop
specify extension add --dev ./extensions/hermes-desktop
specify workflow run      ./workflows/hermes-desktop/workflow.yml
specify bundle add    --dev ./bundles/hermes-desktop

Rules that keep the next merge boring: follow the upstream schema exactly, use strategy: append so presets compose instead of replacing, and keep every hook optional: true by default.

Bundle variants (backend, fullstack, ml, api-only) are planned, not built. Each would compose the base preset with role presets that do not exist yet, so shipping the manifests now would advertise something uninstallable.

8. Scope

Shipped:

  • One guided pane: folder, process, description, step tracker, gate cards, artifact reader.
  • Every workflow action goes through specify workflow run|resume|status; the pane holds

no workflow logic.

  • Non-blocking dispatch: run and resume return a job id, the pane polls run state.
  • Three processes from one pane: SDD (speckit), bug fixing (bug) and idea assessment

(assess). The last two are generated on first use, because the bundled extensions ship commands but no workflow.

  • Gate answers carried by a declared verdict_input, patched into installed workflows by

/init and /repair-workflows.

  • A gate shows the output of the step it reviews, says when that preview is only the end

of a longer stream, and can load the rest.

  • Stop, a per-project run lock, and run history scoped to its own workflow.
  • Artifact listing across <project>/specs/ and .specify/, editable with conflict checks.
  • Folder browser that honours SPECKIT_ALLOWED_ROOTS when an operator sets one.
  • Installer that backs up before it writes, and /integration/health to re-apply the

Hermes integration when an upgrade overwrites it.

  • Ships the three workflows it runs (workflows/), with every gate naming the input it

binds, and installs them into a new project on /init. Spec-kit's own bundled SDD workflow omits that declaration, so its gates accept a resume and discard it.

  • A claim gate: every test count stated in the docs is compared with the suites that just

ran, and a pre-commit hook runs it.

  • 51 node tests, and 118 backend tests: 113 that need only FastAPI and 5 that need Hermes.

Next, in the order I would do them:

  1. Confirm the wizard in the live app. Nothing in the repo can do this: the suites check

that components are wired, not that the pane draws.

  1. Bundle variants (backend, fullstack, ml, api-only) as one-click installs.
  2. A runner for arm64, which is the one platform no CI job covers.

Known gaps, not designed yet. These came out of the earlier review and none has an owner or a shape:

GapWhy it matters

MCP workflow steps (a shell step calling hermes mcp call ...) were sketched earlier and never verified. There is no registry for the workflow engine to read, so it stays an idea, not a plan.

11. The config corruption, and what changed because of it

On 2026-10-24 Hermes refused to start with DuplicateKeyError: found duplicate key "enabled". The cause was scripts/config-enable.mjs. It edits plugins.enabled by text surgery, and its block scan treated any unindented line as the end of the plugins: mapping. Real configs put a column-0 section banner between plugins: and its keys, so the scan stopped early, failed to find the existing list, and spliced a second enabled: in directly under plugins:.

Fixed in accca5d:

  • Column-0 comments no longer end the mapping. That is the bug.
  • The editor refuses to touch a file that already carries two enabled: keys,

instead of appending to the first and writing back something still broken.

  • The self-check applies the same rule, so it cannot report success on a bad edit.
  • Two regression tests use the real banner shape; one of them fails against the old

code with the same signature the corruption had.

Standing rule: any script that edits config.yaml must back the file up first, prove the result parses, and prove the key it wrote appears exactly once.

12. Upstream maintenance

  • Isolation: Hermes additions are new directories and catalog entries. No upstream

file is edited. Core template bugs go upstream as PRs.

  • Sync: merge upstream/main into fork/main. Merge, not rebase, so history stays

intact for anyone tracking the fork.

  • Conflicts: catalogs are the only expected conflict, resolved in favour of our

entries. Anything else fails and gets read by a human.

  • Version pin: speckit_version: "^0.16.0" in the bundle. A major bump gets tested,

not absorbed.

  • Not built: the scheduled sync job, and the CI check that fails on a non-catalog

conflict. Until those exist the merge is manual.

13. Other harnesses

The spec-kit primitives are markdown and YAML, so the distribution layer is portable by construction. A second harness needs three things: a way to invoke a skill, a way to read and write .specify/, and somewhere to put the three steps.

That is a thin adapter, not a rewrite:

invokeSkill(skill, prompt)                    -> result
readFile(path) / writeFile(path, text, mtime)
registerSteps(spec, constitution, tasks)

Candidate harnesses worth naming: OpenClaw, Orca, Codex, Claude Desktop, OpenCode. Their plugin models differ enough that each needs its own adapter. None has been checked against its own documentation, so treat this as a research queue, not a compatibility claim. Hermes is the only one verified here.

What carries over unchanged: templates, preset composition, extension hooks, workflow YAML, and the .specify/ layout. Those are files, not APIs.

Per-harness work, when someone picks one up:

HarnessNeeds beyond the adapter
OpenClawdashboard widget instead of a pane; ACP session templates
Orcapanel HTML in an isolated view; capability declarations for the sandboxed worker
Codexpane layout; MCP UI for any hosted surface
Claude Desktop.claude-plugin manifest; pane layout
OpenCodeterminal rendering plus a web UI path

Checklist for a new harness: implement the adapter, declare capabilities, map speckit-* to its invocation, build the three step surfaces, prove round-trip against a real file, run a workflow, run a hook, install a bundle, and write down the quirks that bit you.
